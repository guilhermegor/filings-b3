# Enforce required status checks + grant the gate `contents: write`

Issue: #116, follow-up to #114. The gate fix in PR #115 made the auto-merge failure **visible**;
this fixes the two causes it exposed.

## What the new logging revealed

```
##[warning]GraphQL error: Resource not accessible by integration
##[warning]auto-merge: NOT enabled — see the GraphQL error above
risk=ci size=M eligible=True state=success
```

A **permissions** error — not the "Pull request is in clean status" I had hypothesised. Worth
recording that the hypothesis was wrong: it was disproved only because the error became visible,
which is the entire value of the #115 change. Reproduced under a plain `workflow_dispatch`
backfill, so it is the workflow's declared permission, **not** the Dependabot token restriction.

## Two fixes, and the order is load-bearing

1. **`pr-gate.yaml`: `contents: read` → `contents: write`.** `enablePullRequestAutoMerge`
   eventually pushes a merge commit to the base branch, so a read-only token is rejected.
   (Fork PRs are unaffected in either direction — GitHub forces their token read-only regardless
   of this block, so this grants nothing to untrusted contributors.)
2. **`REQUIRED_CHECKS` populated.** It shipped `()` — empty *by design*, so the scaffold never
   guesses check names — and was never filled in for this repo. Consequences beyond auto-merge:
   nothing blocked a merge, so **a PR could have merged with red CI**, and the gate's premise
   ("GitHub holds the merge until every required check is green") was simply false here.

⚠️ **The permission fix alone would have been worse than the status quo**: auto-merge would arm
and merge *immediately*, with nothing gating CI. Required checks had to land first or together.

## The required set, and what is deliberately excluded

Populated per the script's documented procedure, from check runs observed on **both** PR shapes —
normal (#115) and Dependabot (#1) — so no name can hang:

| Required | Excluded, and why |
|---|---|
| `lint`, `build` | `Analyze (python)` / `Analyze (actions)` — carry the *real* analysis verdict but exist **only on normal PRs**; requiring one blocks every Dependabot PR forever |
| `Run Automated Tests (ubuntu/windows/macos-latest)` | `Close linked issues of merged PRs` — absent on Dependabot |
| `CodeQL` | `Re-evaluate every open PR (policy backfill)` — `skipped` by design |

**On `CodeQL`** (user's call, defence-in-depth): it is `success` on normal PRs and `neutral` on
Dependabot ones, where CodeQL spawns no `Analyze (…)` runs — so there it satisfies the
requirement **vacuously**, meaning "no analysis performed" rather than "analysis passed". Uniform
enforcement across PR types comes from the ruleset's own `code_scanning` rule
(`alerts_threshold: errors`, `security_alerts_threshold: high_or_higher`), which gates on alert
severity and is independent of check runs.
